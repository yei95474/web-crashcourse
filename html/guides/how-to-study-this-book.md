# How to Study This Book

[Course home](../HTML_CRASH_COURSE.md)

This course is designed for active practice. HTML looks simple when read and becomes meaningful when typed, broken, inspected, and repaired.

Before Chapter 1, take the [entry diagnostic](../assessments/course-assessments.md#entry-diagnostic). It does not decide whether you belong in the course. Use it to identify unfamiliar vocabulary and choose whether to follow the intensive, standard, or steady schedule.

## Prepare one study session

Use the current chapter's suggested study time to plan one or more sessions. Most chapters need 30-75 minute blocks; projects need several blocks. Open:

- The current chapter.
- Your code editor and course workspace.
- A browser.
- A paper notebook or plain-text learning journal.

Remove unrelated notifications. Decide on one target, such as “complete Sections 6.1-6.4 and calculate three relative paths.”

## Use the six-pass method

### 1. Preview

Read the objectives, headings, and mastery checklist. Predict what the chapter connects to.

### 2. Read

Read one small section. Pause when a new term appears. Add it to your notes in your own words.

### 3. Type

Type examples rather than copying whole blocks. Typing makes punctuation and nesting visible. Compare only after attempting the code.

### 4. Change

Alter one meaningful detail:

- Change content.
- Add a sibling.
- Move a file and repair its path.
- Remove an attribute and predict the effect.

State your prediction before refreshing.

### 5. Retrieve

Close the example and reproduce its essential pattern from memory. Retrieval is more powerful than rereading.

### 6. Review

Complete the exercises and mastery checklist. Record one mistake and the rule that explains it.

## Productive use of answer keys

When stuck:

1. Read the prompt literally.
2. Identify the chapter concept being tested.
3. Reduce the problem to the smallest example.
4. Inspect a related worked example.
5. Make one attempt.
6. Then consult the relevant answer explanation.

After reading a solution, close it and solve the problem again from a blank file. Recognition is not recall.

## Keep a learning journal

For each session, record:

```text
Date:
Chapter:
What I built:
One concept I can explain:
One mistake and its cause:
One question:
Next action:
```

Questions should become increasingly precise. “Why doesn't it work?” can become “Why does `pages/contact.html` resolve `images/map.png` beneath `pages/`?”

## Use spaced review

Revisit material after increasing intervals:

- End of the same session.
- Next day.
- One week later.
- During the next project.

Review by producing or explaining, not only rereading. Draw a document tree, build a skeleton, calculate a path, or audit a form.

## When to move forward

Move on when:

- You can explain the main idea without the chapter.
- You can modify an example without losing its structure.
- You can complete most warm-up and core questions.
- You know where to verify details you have not memorized.

Do not demand perfection before continuing. Later projects deliberately revisit earlier skills.

## When to slow down

Pause and review when:

- Closing tags and nesting still feel random.
- You cannot find your active file.
- Paths are being guessed.
- Elements are chosen only by appearance.
- You copy complete solutions without explaining them.

Return to the last mastery checklist you cannot defend.

## Getting help well

A strong help request includes:

- Goal.
- Minimal relevant source.
- Directory tree if paths are involved.
- Expected result.
- Actual result.
- Checks already attempted.

Never publish passwords, API keys, personal records, or private messages in a help request.

## A final rule

Build something small after every chapter. Knowledge that never changes a document is still fragile.

After the 20 core chapters, use the optional appendices selectively. Read an appendix because your project has a performance, privacy, platform, browser, or assistive-technology question—not merely to collect more syntax.

Finish with the [final assessment](../assessments/course-assessments.md#final-assessment). If one component is weak, use its outcome map to select review chapters, repair the evidence, and reassess with new content.
